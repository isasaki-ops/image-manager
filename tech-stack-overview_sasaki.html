5. 構成の新旧グルーピング

① Vercel + Supabase 系（比較的新しい・共通化しやすい構成）

  • image-manager — Next.js / Supabase / R2、GitHub連携で自動デプロイ済み
  • pachinko-crm — Next.js / Supabase Auth、GitHub連携済みだが未commit変更が滞留
  • paa / pmp-tool — Python(Flask) / Supabase だがGitHubリモート未接続。技術選定は新しい構成側だが、バージョン管理の運用が伴っていない
  • scheduled-banner-system（banner-console部分） — Vercelにはデプロイされているがgit管理そのものが存在しない。新構成の皮を被った最も属人化リスクが高いケース

② 自前サーバー・手動デプロイ系（従来型・属人化しやすい構成）

  • god-lp — Xserverへの手動FTPデプロイ（deploy.py）。GitHubにはpushしているが14コミット分の遅延あり
  • scheduled-banner-system（scheduled-bannerプラグイン部分） — zipファイルの手動アップロードで配布、バージョン管理なし
  • pachislot-writer / banner_generator — ホスティング対象外のローカルCLIツール。デプロイという概念自体がないが、pachislot-writerはGitHub連携ありに対し、banner_generatorはローカルgitのみで誰にも共有されていない
  • fuzai — バージョン管理なし、デプロイ先も未確認の最も簡易な構成

今後の方針としては、①のVercel + Supabase構成に技術選定は寄っているが、 「デプロイ先だけ新しくして git 運用が追いついていない」プロジェクト（paa/pmp-tool、scheduled-banner-system）が最大のリスク。 まずはこの2つにGitHubリモートの設定を行うことが、属人化解消の優先度が高いと考えられる（本レポート作成者所見・推測）。

出典・確認方法

  • 各プロジェクトの package.json / requirements.txt / CLAUDE.md / README.md / .gitignore / .env.example を直接読んで確認
  • デプロイ設定は vercel.json、.vercel/project.json、deploy.config.json（god-lp）、scheduled-banner.phpのプラグインヘッダーコメントから確認
  • バージョン管理状況は各プロジェクトディレクトリで git remote -v / git branch -a / git log --oneline / git status -sb を実行して確認
  • GitHubアカウント種別は gh auth status と gh api users/isasaki-ops（type: User）で確認、リポジトリ一覧は gh repo list で確認
  • Vercelのチーム・プロジェクト情報は vercel whoami / vercel teams ls および各プロジェクトの .vercel/project.json から確認
  • .env系ファイルは存在有無と変数名のみを確認し、値は一切読み取っていない（paa/.env.local: ANTHROPIC_API_KEY, VERCEL_OIDC_TOKEN など、変数名のみ列挙）
  • god-lpのdeploy.config.jsonにはFTP接続情報（ホスト名・ユーザー名・平文パスワード）が含まれることを確認したが、値はこのレポートに一切含めていない。.gitignore対象で追跡されていないことも確認済み
  • pmp-sender関連ファイルにBasic認証情報のサンプル値が記載されていたが、同様に値は非開示としている
